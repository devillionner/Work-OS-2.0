## Migration fixes required by this real backup

The cutover must include the following fixes already merged into `main` before importing production data:

1. Preserve Telegram account ownership when legacy assignment-map keys are lowercase while URL paths/invite codes preserve original casing.
2. Start a new migration job with the `accounts` phase before `chats`, so TG2 exists before foreign-key references are written and the selected account can be restored.
3. Reconstruct `chat_joined` events from `joinedAt`, attribute Telegram responses/bookings to the source chat account where known, keep unknown attribution nullable, and repair publication/event account attribution during repeat synchronization.
4. Preserve the raw `telegram-multi-account-v1` value in `user_settings` in addition to normalized account/chat ownership so later cloud backups retain the remaining legacy account metadata during cleanup.

## Cutover acceptance criteria

Do not retire Prototype Checker as the working fallback until all of these are true:

1. The uploaded staging copy reports the exact SHA-256 from this document.
2. The importer preview matches the control totals above or every difference is explicitly explained.
3. The normalized migration reaches `completed` without skipped phases.
4. Post-import database counts match the expected migration totals, allowing only documented pre-existing cloud records that are matched/upserted rather than duplicated.
5. TG1/TG2 chat ownership and the selected Telegram account are spot-checked against the source backup.
6. Historical publication, response, booking and chat-join analytics are spot-checked across multiple dates and platforms.
7. A Work OS cloud backup can be exported after cutover and contains the normalized domain tables plus legacy settings needed for ongoing cleanup.

After these checks pass, the local Prototype Checker files are no longer an operational dependency. The original source backup may still be retained offline as an immutable disaster-recovery artifact.
