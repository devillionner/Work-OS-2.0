# Локальні перевірки та контроль D1

Усі автоматичні тести, restore-drill, migration rehearsal та навантажувальні перевірки виконуються локально. Для поточного набору достатньо Node.js 22.13+ та встановлених залежностей; Cloudflare login і production backup не потрібні.

```sh
npm ci
npm run verify
```

`verify` послідовно виконує lint, Node tests з локальним Miniflare та build; прибирає успадковані Cloudflare credentials і вибір production environment з дочірніх процесів. Він не викликає deploy або migration runner. Це захист стандартного workflow, не мережева sandbox: credentials з локальних файлів/конфігів не слід використовувати в тестах. Tests використовують синтетичні записи `example.test`; production D1 не є fixture.

Для локального ручного preview:

```sh
npm run db:migrate -- --database DB --local
npm run dev
```

Не задавати `CLOUDFLARE_ENV=production`, не вмикати `remote: true` у binding і не запускати `wrangler dev --remote`. Для тесту на чистій базі створити окремий Miniflare instance; не очищувати існуючі бази або єдину локальну копію користувача.

Це відповідає [Cloudflare D1 local development](https://developers.cloudflare.com/d1/best-practices/local-development/): Miniflare і локальний D1 дозволяють перевіряти поведінку до deploy. Конкретні квоти/ціни перевіряються перед release, не фіксуються як незмінна обіцянка.

## Remote operations

Remote міграції не є тестовою командою. Runner відмовляється працювати в CI; поза CI потребує `--remote --allow-remote --reason <конкретна-причина>`, а production також `--allow-production`. Ці прапорці документують намір оператора і не замінюють прямого дозволу користувача. Перед запуском потрібні конкретні target/config, актуальна копія, локальна перевірка та release/recovery plan. Повторний resync/restore без нової причини заборонений.

Runner припиняє роботу, якщо не зміг прочитати журнал застосованих міграцій. Він не вважає невідомий результат порожнім списком і не запускає всі SQL повторно. SQL і marker поки окремі операції: при перериванні між ними потрібна ручна перевірка, не сліпий повтор.

## Поточне зменшення запитів

- GET таймерів лише читає: completed визначається з `ends_at`. Фактичне закриття лишається явним POST; raw backup може містити `running` із минулим deadline — це коректний збережений стан.
- Відлік щосекунди локальний. Таймери синхронізуються не частіше разу на 120 секунд, лише у видимій online-вкладці, без перекриття запитів. Помилки не запускають швидкий повтор. Зміни з іншого пристрою можуть з’явитися із затримкою до 120 секунд; це не real-time subscription.
- Завершення таймера не викликає повторний GET. Запізнілий GET не перекриває локальний start/dismiss.
- Повтор після завершення Telegram-перерви також обмежений 120 секундами; збій мережі не створює запит щосекунди.
- Перевірка query plans/rows read решти API — OPS-06 у roadmap. Зменшення реального рахунку Cloudflare не заявляється без production-вимірювання.
